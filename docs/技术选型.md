# 技术选型

> **决策日期**：2026-08-05
> **开发模式**：单人 + AI agent
> **引擎**：Godot 4.7.1
> **语言**：GDScript

---

## 一、决策依据

| 维度 | Godot 4 + GDScript | 选择理由 |
|------|-------------------|---------|
| 授权 | MIT 开源，无授权费 | 单人开发成本敏感 |
| 2D 能力 | 原生 2D 节点、TileMap、动画 | 肉鸽生存是 2D 为主 |
| agent 友好度 | GDScript 语法简洁、动态类型、agent 生成准确率高 | 最大化 agent 编码效率 |
| 迭代速度 | 编辑器启动 <3s、热重载、单文件工程 | 单人快速试错 |
| 生态 | 社区有 survivor-like 开源参考 | 可借鉴成熟模式 |
| 跨平台 | 一键导出 Win/Mac/Linux | MVP 阶段足够 |

**不选 Unity**：启动重、个人版有收入门槛、C# 虽 agent 友好但 Unity API 样板代码多
**不选 Phaser**：大量实体（350+ 敌人）性能需手动优化、无编辑器、肉鸽生态弱
**不选 Bevy**：Rust 学习曲线陡、agent 对 Rust 游戏代码生成较弱、生态新

## 二、架构设计

### 2.1 总体架构：节点系统 + 对象池（非 ECS 框架）

> **不引入第三方 ECS 框架**（如 RelEcs）。Godot 原生节点系统 + 代码层对象池在 GDScript 中更高效，且 agent 生成准确率更高。

```
Main (SceneTree)
├── World
│   ├── Player                    # 玩家节点
│   ├── EnemySpawner              # 刷怪器
│   ├── EnemyPool                 # 敌人对象池（预分配 500）
│   ├── ProjectilePool            # 投射物对象池（预分配 300）
│   ├── ParticlePool              # 粒子对象池（预分配 200）
│   ├── PickupPool                # 拾取物对象池（经验珠/潮币）
│   └── SpatialHash               # 空间哈希网格（碰撞查询）
├── UI
│   ├── HUD                       # 血条/武器槽/经验条/夜数
│   ├── DayPhaseUI                # 抉择之昼（三选一/商店/事件）
│   └── ResultUI                  # 结算/死因
├── GameState                     # 单局状态（autoload 单例）
└── SaveSystem                    # 存档系统（autoload 单例）
```

### 2.2 对象池实现

- 预分配：场景加载时 `preload` + `instantiate` 填充池
- 获取：`pool.acquire()` → 激活节点 + 重置状态
- 回收：`pool.release(node)` → 失活节点 + 移出场景树（或 hide）
- **禁止运行时 `instantiate`**（GC 压力）

### 2.3 数据驱动

- `config/` 目录为唯一数据源
- 武器/敌人/Boss/事件配置：JSON 文件（`config/weapons.json`、`config/enemies.json` 等）
- 经验表：`config/exp_table.json`（由 `tools/generate_exp_table.py` 生成）
- 运行时启动加载到 `GameState` 单例，运行中只读

## 三、性能策略

### 3.1 渲染优化

| 对象 | 策略 | 目标 |
|------|------|------|
| 同种敌人（350+） | `MultiMeshInstance2D` 批量渲染 | 单 draw call / 种类 |
| 投射物 | `MultiMeshInstance2D` 或 `CPUParticles2D` | 减少 draw call |
| 粒子 | 全局池 200 实例 + 优先级回收 | 见疑点清单 Q12 |
| UI | CanvasLayer 分层 | 不与 World 混渲染 |

### 3.2 碰撞优化（不用 Godot Physics2D）

> Godot Physics2D 在 350+ 敌人时性能差。改用自定义空间哈希。

- 网格尺寸 = 敌人半径 × 4（约 80 游戏单位）
- 敌人↔敌人：仅分离检测（排斥向量），不做物理碰撞
- 投射物↔敌人：投射物查所在网格 + 8 邻格
- 实现：`SpatialHash` 类，`Dictionary` 存储 `Vector2i → Array[Node]`

### 3.3 AI 分帧更新

| 分组 | 更新频率 | 包含 |
|------|---------|------|
| 远程敌人 | 每 1 帧 | 潮汐召唤师（需持续更新目标位置） |
| 近战敌人 | 每 2 帧 | 小水鬼/铁壳蟹/深潜者 |
| 小怪/Boss 召唤物 | 每 4 帧 | 水母浮游/爆炸贝/毒水母 |

### 3.4 性能预算

| 指标 | 目标 | 验证方式 |
|------|------|---------|
| 同屏敌人 | 350~450 @ 60fps（PC） | `Engine.get_frames_per_second()` 监控 |
| 内存 | ≤ 512MB | `Performance.get_memory()` |
| draw call | ≤ 100 | Godot 调试面板 |
| 物理/碰撞 | 自定义哈希，不走 Physics2D | 代码审查 |

## 四、确定性 RNG

### 4.1 实现

- 使用 Godot 内置 `RandomNumberGenerator`（基于种子，确定性）
- 全局单例 `RNG`，所有随机决策走此单例
- **整数采样优先**，避免浮点跨平台误差

```gdscript
# rng_singleton.gd (autoload)
extends Node
var _rng := RandomNumberGenerator.new()

func set_seed(seed_value: int) -> void:
    _rng.seed = seed_value

func rand_int(min_val: int, max_val: int) -> int:
    return _rng.randi_range(min_val, max_val)

func rand_float() -> float:
    return _rng.randf()

func weighted_pick(items: Array, weights: Array) -> Variant:
    # 整数权重采样，用于三选一/掉落
    ...
```

### 4.2 种子管理

- 普通局：`randi()` 生成 32 位种子，存入存档
- 每日挑战（抢先体验）：服务器下发固定种子
- 同一种子 + 同一版本 = 完全一致的游戏状态

## 五、存档系统

### 5.1 格式

```json
{
  "version": 1,
  "saves": [
    {
      "character": "watcher",
      "lighthouse_level": 3,
      "stardust": 1250,
      "unlocks": ["ironclad", "stargazer"],
      "settings": {"language": "zh", "volume": 0.8},
      "seed": 1234567890,
      "last_played": "2026-08-05T12:00:00Z"
    }
  ]
}
```

### 5.2 迁移策略

- 读取后检查 `version` 字段
- 若 `version < current`，按版本号逐步执行迁移函数
- 示例：`_migrate_v1_to_v2(save_data)` 为旧存档补 `refine_level: 0`

### 5.3 冲突解决（Steam 云同步）

- 时间戳较新版本覆盖（默认）
- 两侧时间戳差 <5 分钟 → 弹窗手动选择

## 七、agent 协作模式

### 7.1 agent 擅长（充分委托）

| 任务 | agent 角色 | 效率倍率 |
|------|-----------|---------|
| 脚手架代码生成 | 生成初稿，人工审查 | 3-5× |
| 数据驱动配置表 | JSON 模板填充 | 5× |
| 重构 | 批量改名、提取函数 | 4× |
| Bug 定位+修复 | 读日志 → 定位 → 修复 | 2-3× |
| 测试用例生成 | 单元测试 + 边界用例 | 3× |
| 文档维护 | 更新变更、同步数据 | 4× |

### 7.2 人工不可替代（重点投入）

| 任务 | 原因 |
|------|------|
| 玩法调优 | 手感、节奏、难度曲线需主观判断 |
| 美术资源 | agent 无法生成游戏美术（用 Kenney.nl 占位） |
| 架构决策 | 跨模块影响需全局视角 |
| 试玩验证 | 体感问题只有玩过才知道 |

### 7.3 每日工作流

```
上午（人工主导）：
  09:00-09:30  规划今日任务（参考周计划）
  09:30-10:00  agent 生成框架代码 / 配置表
  10:00-12:00  人工实现核心逻辑 + agent 辅助填充

下午（agent + 人工）：
  14:00-16:00  agent 生成测试用例 + 辅助调试
  16:00-17:00  人工调优手感 / 试玩
  17:00-17:30  agent 更新文档 / 提交代码

周五：
  14:00-14:30  最小可玩版本试玩
  14:30-15:00  复盘 + Bug 列表
  15:00-17:00  agent 批量修 Bug
```

## 八、风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| GDScript 性能不达标（350 敌 60fps） | 中 | MultiMesh + 空间哈希；若仍不达标降至 250 敌上限 |
| agent 生成代码有隐 Bug | 高 | 人工审查 + 单元测试 + 每周五试玩 |
| 单人决策瓶颈 | 中 | agent 提供方案对比，人工拍板 |
| 美术资源缺失 | 高 | W1-W18 全用占位图（Kenney.nl），W19 统一替换 |
| 范围蔓延 | 中 | 严格守 MVP 红线，P2 全砍 |
